# 汉字密文固定开头 `犯之说浙没` — 成因与「指定开头」方案

> 状态：**仅记录，未实施**。本文档只描述现象成因与可选方案，代码未改动。
> 相关代码：[src/core.js](../src/core.js) `HanziCodec.encode/decode`、[src/cx2.js](../src/cx2.js) 包头、[src/hanzi-table-v2.js](../src/hanzi-table-v2.js) 字库。

---

## 一、现象

汉字密文的前几个字几乎总是「犯之说浙没」，且同一前缀对应唯一的密文长度。

实测反解（字库 `HANZI_TABLE_V2`）：

```
L=3926 → 犯之说浙没      ← 密文总长 3926 字节（明文 3795B，收件人 N=1）
L=3927 → 犯之说装没
L=3925 → 犯之说税没

穷举 L ∈ [0, 200000]，前缀 = 犯之说浙没 的解**唯一**：L = 3926
```

字库序号：`犯`=536，`之`=0，`说`=30，`浙`=1376，`没`=256。

---

## 二、成因

**长度头是明文写在位流最前面的，且前 5 个字 100% 不含随机成分。**

[src/core.js](../src/core.js) 的 `encode()` 在字节流最前面写入 5 字节长度头：

```js
const head = [0x43, (len >>> 24) & 0xFF, (len >>> 16) & 0xFF, (len >>> 8) & 0xFF, len & 0xFF];
```

紧随其后的是 CX2 的 3 字节包头 `ver(0x02) ‖ flags(0x00) ‖ N`（[src/cx2.js](../src/cx2.js)）。
**8 字节 = 64 bit，而 11 bit/字** → 前 5 个字完全由这 64 bit 决定，第 6 个字只差 2 bit 就落入随机区。
第一份随机数据（`idx`，第 11 字节起）要到**第 7 个字**才参与运算。

### 位布局（逐字节 XOR 验证）

| 汉字 | 覆盖位 | 承载内容 | 取值 |
|---|---|---|---|
| 第1字 | 0–10 | `0x43<<3` \| `L>>>29` | **恒为 `犯`**（L < 512MB 时） |
| 第2字 | 11–21 | `(L>>>24 & 0x1F)<<6` \| `(L>>>18 & 0x3F)` | **L < 256KB 时恒为 `之`** |
| 第3字 | 22–32 | `(L>>>16 & 3)<<9` \| `((L>>>8) & 0xFF)<<1` \| `(L>>>7 & 1)` | 随 `floor(L/256)` 变；`说` 对应 L1 = 0x0F |
| 第4字 | 33–43 | `(L & 0x7F)<<4` | 随 `L mod 128` 变；`浙` 对应 86 |
| 第5字 | 44–54 | `(0x02 & 0x0F)<<7` | **恒为 `没`**（CX2 版本号 0x02 → 索引 256） |
| 第6字 | 55–65 | `(flags&1)<<10` \| `N<<2` \| `idx[0]>>>6` | flags=0 且 N 固定时只有 4 种 |

验证（改动单个 header 字节，观察前 6 字哪一位变化）：

```
基线 L=3926,N=1 :  犯之说浙没以
0x43  ^=1       :  庆之说浙没以     ← 只影响第1字
L3    ^=1       :  犯至说浙没以     ← 只影响第2字
L2    ^=1       :  犯之害浙没以     ← 只影响第3字
L1    ^=1       :  犯之他浙没以     ← 只影响第3字
L0    ^=1       :  犯之说装没以     ← 只影响第4字
0x02  ^=1       :  犯之说浙力以     ← 只影响第5字
flags ^=1       :  犯之说浙没该     ← 只影响第6字
N     ^=1       :  犯之说浙没之     ← 只影响第6字
```

**结论**：这不是随机性缺陷，而是设计使然 —— 长度头必须可被解码端无歧义读出，故明文居于位流前端。真正的问题是**前 5 字完整暴露了「明文长度 + 协议版本 + 收件人数」，且与明文内容、密钥、随机数全部无关**。同长度的两条消息共享同一前缀，外部只需观察密文即可读出长度、做消息对号，无需解密。

## 三、方案：指定开头（未实施）

目标：让密文以使用者指定的几个汉字开头（如「秘制」），同时不引入新的长度泄露。

### 硬约束：`指定字数 ≤ 4`

汉字区 11 bit/字，长度头必须紧跟前缀。若要**同时**隐藏长度头，则：

```
88 bit（8 字对齐点） - 11×N（前缀） ≥ 40 bit（掩码长度头的随机窗）
→ N ≤ 4
```

若放弃隐藏长度头，前缀可任意长。

### 方案 E：内嵌前缀块（推荐）

把前 128 bit（16 字节，约 11.6 字）重构为：

```
[ banner: 11N bit ][ random: 88-11N bit ]   ← 共 88 bit，天然是 8 字对齐点
[ head XOR mask : 40 bit ][ 补 0 至 128 bit ]
```

`mask` 取随机段的前 40 bit。基准点 88 bit 天然对齐，长度头**不会跨字错位**，这是该方案成立的关键。

接收方**无需知道前缀长度**：试 `N = 0..4`，扫描前 12 字校验 `magic == 0x43` 与长度自洽，实测唯一命中。

已验证（临时脚本，字库真实加载）：

```
指定前缀 "秘制安全"
  payload  131B → 秘制安全仗〔陈Ω↗〔石Ⅻ
  payload 1031B → 秘制安全夺史蛮娶津史韦波
  payload 3031B → 秘制安全烦宇同姻誓宇还恨

同前缀、不同长度，第 9 字起完全随机：
  L=1031 → 吏ⓐ乾      L=1032 → 展⌓↙

压力测试 N=0..4，30000 次随机长度/人数：歧义 0，最多候选 1
```

开销（汉字密文总字数，恒定与消息长度无关）：

| 明文字节 | 现状 v2 | 方案 E (N=4) | 差值 |
|---|---|---|---|
| 100 | 99 | 107 | +8 字 |
| 1000 | 754 | 762 | +8 字 |
| 3795 | 2787 | 2795 | +8 字 |

来源：前缀块 16B vs 原长度头 5B = +11B ≈ 8 字。可缩小前缀块省字数，但会压低 N 上限。

**分段交互已核对**：[src/text-crypto.html](../src/text-crypto.html) 的 `SEG_ALIGN: 8`（88 bit 周期）在新格式下依然成立 —— 前缀块 16 字节，切片仍按字符切、拼接后位流连续。

### 方案 I：纯前置（不推荐）

```
"秘制安全" + 原密文
```

- 优点：实现最简单，可指定**任意字数**（实测 N=8 仍唯一命中）
- **缺点：长度头依旧裸露**（第 4~8 字仍承载 `L4..L0`），原问题未解决
- 接收方须靠 `bytes.length - 5 - L ∈ {0,1}` 的**容差启发式**判据反选 N（11 bit 对齐补位最多多 1 字节），比方案 E 的严格等式脆弱

### 向后兼容

两种方案都会让**已发出的汉字密文失效**（前缀改变了位流起点）。可选做法：

1. **不兼容** —— 与项目历史上 v1→v2 的做法一致
2. **兼容** —— 解码时先试新格式，失败回退旧路径，接收侧多一个分支

待定，暂不实施。

## 四、顺带发现的缺陷

`HanziCodec.isHanzi()`（[src/core.js](../src/core.js)）判定阈值：

```js
if (s.length < 8) return false;   // 至少 8 字才够 11 字节
```

但解码需要 `0x43` 头 5 字节 + 至少若干 payload，8 个汉字 = 88 bit = 11 字节，减去 5 字节头仅剩 6 字节，而 `decode()` 要求 `bytes.length >= 5` 且 `origLen <= bytes.length - 5`。**该阈值偏低**，且当前判据是「全串 2048 字扫描」——自然中文短句理论上可能撞入。

建议改为结构判据：先试 `decode()` 校验 `magic == 0x43` 且长度头自洽，命中即密文，否则立即否决。更快也更准。
