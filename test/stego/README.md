## 二、对原规范的 5 处修正（已落到代码）

### ① `forward()` 必须返回 **top-K（K>64）**，不能只返回 top64〔硬阻塞〕

原规范接口是 `top64: Uint16Array`，同时又说"由第 65 名递补补齐 64 个"。
**两者矛盾**：过滤器会剔掉字符集不符 / 前缀冲突的 token，剔完必须递补，
但只给 64 个就**没有第 65 名可取**，过滤器必然 starved。

现接口：`forward(lastTokenId, state) -> { topK: Uint16Array, nextState }`，`topK` 默认 **256**。
（`candidates.mjs` 在 raw 不足时会显式抛 `CANDIDATE_STARVED`，绝不静默给短集。）

### ② 固定 Magic 会复活「犯之说浙没」指纹〔致命〕

原规范把固定 Magic `0x5354` 放在载荷最前。**载荷最前就是位流最前**，
于是每段的首 2 个 token 由固定 12 bit 决定；又因 BOS 固定为 `[1]`，
**每条密文的伪装文本都带同一个固定两词开头** —— 正是 `docs/hanzi-prefix.md`
记录的指纹，只是换了个位置复发，而且更显眼。

对策：`首 2 字节 = Magic ⊕ nonce`，`nonce = fnv1a16(msgid + '/' + seq)`，
**由明文段头里已有的字段派生，不新增字段、不改信封格式**。

实测（T7，N=200）：首 token 覆盖 **52/64** 个名次；对照组把 nonce 固定后离散度显著塌缩。

### ③ 66 字节桶 与 192 字节段 互斥〔结构性冲突〕

原规范同时给了两个粒度：桶 66B、单段 192B。但 **192 % 66 ≠ 0**，两者不能共存。

现方案**合并为一个概念：段长 = 桶长 = 192 字节**。
- `192 × 8 = 1536 bit = 256 × 6 bit` → 整除，无残位
- `192 % 3 == 0` → 满足 `8B % 6 == 0` 的必要条件

> 原规范选 64 字节是错的：`64 × 8 = 512`，`512 % 6 = 2`，留 2 bit 残尾（T1 已断言）。
> 若确需 66 字节粒度，段长应改为 `198 = 3 × 66`。

### ④ PRF 填充**不隐藏长度**（原规范的目标达不成）

原规范称 PRF 填充"彻底掩盖真实载荷边界"。但 `Len` 字段就明文躺在载荷里
（offset 2..3），**任何拿到模型的人都能直接读出长度**，根本不需要分析填充。

PRF 填充保留（成本为零，且让尾部不是一片 0，对"知道有此方案但无模型"的观察者有效），
但**长度遮蔽实际来自"每段都凑满 192 字节"**，不是填充。

> 另需明确：**隐写层不提供机密性**。持有模型 + 词表的人可把任何伪装文本还原成字节流，
> 不需要任何密钥。安全性 100% 由 CX2 的 AES-GCM 承担，隐写只是表观混淆。

### ⑤ 「删一个补一个」一趟不闭合〔算法缺陷〕

原规范：Top-64 内若出现 `我`/`我们`，只保留 rank 更高者，空位由第 65 名递补。
但**第 65 名自己可能又和集合内成员冲突**，一趟递补不闭合，需要迭代到不动点。

现实现改为**单趟贪心扫描**：沿原始排序从头扫，凡与已接受集兼容就收，收满 64 即止。
天然闭合、必然终止。

> **prefix-free 充分性可证**：设编码端发出候选 `c`，解码端游标处文本 `T` 以 `c` 开头。
> 若另一候选 `c'` 也是 `T` 的前缀：
> `|c'| ≤ |c|` → `c'` 是 `c` 的前缀；`|c'| > |c|` → `c'` 越过 `c` 进入下一 token，故 `c` 是 `c'` 的前缀。
> 两种情形都被 prefix-free 排除 ⇒ 命中唯一。∎

## 三、补充的两条约束

**a) 换行禁令已被字符集白名单覆盖。**
白名单 = CJK 统一汉字 + 中文标点，**空格 / 换行 / ASCII 一律拒**。
所以"禁用换行"不是独立过滤器，而是白名单的真子集（`candidates.mjs` 里两者都在，冗余但显式）。
这带来一个额外好处：既然 token 内**不可能**含空白，解码端就能**安全地剥离一切空白与零宽字符**——
不仅免疫 `\r\n`，连平台插入的空格、零宽空格一并免疫（T9 实测四类污染全部还原）。

**b) Fast-Fail 需要双闸，原规范只有一闸。**
原规范只检查"演满 2 步后 Magic 位是否匹配"。但普通中文文章通常**第 1 步就走不动了**
（没有任何候选是当前文本的前缀）——这本身就是强否定信号，应当立刻退出。

现 `decodeFrame` 双闸：
- 闸①「走不动」：`hits === 0` 且步数 < 4 → 立即判 `NOT_STEGO`
- 闸②「值不对」：演满 2 步但 Magic 位不匹配 → `NOT_STEGO`

实测（T8）：三篇普通中文文章**最坏 1 步**推理即被拒（对比全量 256 步）。
普通文章撞进闸②的概率约 `1/4096`，撞进后也只会跑到段尾，代价可接受。

## 四、实测指标（mock 词表，`avg_token_bytes = 6.93 B`）

膨胀率对**载荷**：`8 × 6.93 / 6 = 9.24x`
（每 token 承载 6 bit；token 平均 6.93 UTF-8 字节 ≈ 2.3 汉字）

对**明文**（含 CX2 131B 固定开销 + 192B 段尾对齐）：

| 明文 P | 膨胀 |
|---|---|
| 200 B | 15.3x ⚠ |
| 500 B | 11.7x ⚠ |
| 1000 B | 10.5x ⚠ |
| 2000 B | 9.8x |
| 3000 B | 9.6x |

### ⚠️ 10x 目标在短消息上必然破线

**判定线：`avg_token_bytes ≤ 7.5` 才能守住 10x（对载荷）。**
本 mock 的 6.93B 已经贴着上限，而**对明文**的倍率还要再乘 `(P+131)/P`。

结论：**10x 只在 P ≳ 2000B 时成立**。短消息的膨胀由两个固定项主导，与 token 长度无关：
- CX2 固定开销 **131B**（单收件人）
- 每段末尾对齐浪费最高 **187B**

**必须做的事（模型到货后第一件）：**
1. 用真 `vocab.bin` 实测加权 `avg_token_bytes`（按 top-64 实际命中分布加权，不是全表平均）；
2. 若 > 7.5，回头与模型端谈**词表长度分布**（少放 3~4 字 token）；
3. UI 必须**按段数显示预估长度**，并对短消息给出"至少需要 N 字伪装文本"的提示。

### 其它实测

- 全链路回环 **1..3000 字节全通**，含 **13,025,280** 次 mock 推理（235s）
- 满段恰好 **256 步**，每步命中数恒为 **1**（prefix-free 生效）
- Fast-Fail 最坏 **1 步**（对比全量 256 步）
- 对抗样本每步轮转植入（`我`/`我们`、`系`/`系统`、`好\n`、`\n`、`。\r`、` 好`、`abc`、`123`），全程精确还原
